# KiteMarket v1.1 candidate user guide

This guide describes the v1.1 candidate implementation. It is not a release announcement or a claim that every live environment has passed verification. Final artifacts, verification scope and release notes govern the supported release. See [UPGRADING.en.md](https://www.kitemc.com/en/kitemarket/operations) for installation and existing data; a seamless upgrade from v1.0.0 is not promised.

Candidate entrances include `/km lots` (bundles/bulk publication), `/km automation`, `/km community` and `/km prices`. Administrators use `/km risk` for audit views and `/km tools` for management writes. Feature permissions and confirmation still apply.

## Installation and existing markets

Fresh v1.1 installations use an independent server/plugin data directory. A durable SQLite file is the default for one market node; shared markets use an independent, empty MySQL/MariaDB database. Do not run multiple game nodes against one SQLite file. Node IDs must be unique, while market identity, game version, item profile and currency identities remain consistent.

Existing MySQL/MariaDB configuration is preserved. Before handling an existing market, back up its complete database, configuration, original runtime, player data and economy data, then verify migration and recovery on an independent copy before planning a cutover. Preserve orders, wallets, frozen funds, claims and unresolved evidence. Do not delete the database, overwrite its identity with fresh configuration, edit balances, repeat activation or mix old and new protocols.

The base plugin provides a complete vanilla GUI. Developers can build their own ItemsAdder interfaces through configuration and the public Java SDK. The host still supplies real items, protected actions, permissions and trading confirmations.

Choose trading modes in the configuration file. For an auction-only market:

```yaml
market:
  enabled-types: [AUCTION]
```

The default `[BUY, SELL, AUCTION]` enables procurement, fixed-price sales and auctions. Keep at least one mode. Empty lists, unknown modes and non-list values are rejected; an invalid reload retains the previous valid policy. Home, publication, bundles and administrator listings offer only enabled modes. Commands and SDK requests cannot bypass this setting. Procurement-only markets hide bundle/bulk publication.

Use the same setting on every node of a shared market and run `/km reload` on each. A node with an outdated policy revision refuses new trades. Disabling a mode does not cancel existing orders, extend their duration or clear the market. Existing orders remain readable and retain normal owner cancellation, expiry return and settlement of existing auction bids. Wallets and claims remain usable.

## Items, bundles, bulk listing and containers

| Operation | Quantity and price |
| --- | --- |
| Fixed-price single items | Unit price multiplied by the selected quantity; partial purchases allowed |
| Procurement | Unit price multiplied by supplied quantity; actual delivered items must match every condition |
| Auction | A bid is the total for the complete auction lot |
| Bundle | Several actual assets form one indivisible lot; the price covers the entire bundle |
| Bulk listing | Several independent orders with individual previews, fees and outcomes |

Sellers can choose a minimum purchase quantity. If the remaining amount falls below it, the whole remainder must be purchased. A bundle cannot be purchased in pieces. Matching materials alone do not make items with different properties equivalent.

Container previews show saved contents without letting players take items from the preview. Unsupported structures, excessive nesting or failed item round trips reject admission. Presentation changes cannot override that result. Sold, returned and expired items enter claims as actual assets. Insufficient inventory space leaves them available to claim later.

Published bundle details open the saved contents and actual quantities; verified container entries open further read-only previews. Claims support source filtering and pages. Select individual entries or the current page, inspect details and confirm at most 36 entries. Items that do not fit remain available. Uncertain outcomes, session changes or disconnects stop subsequent entries without repeating delivered items or continuing into other pages.

Each bulk order still requires manual confirmation. Unpublished selections and batch plans remain in the current session without automatic resumption after logout or restart. Executed operations, funds and outcomes persist.

Current publication policy checks the full selected quantity for single items, each independent group for bulk listings and one lot for a bundle. Quantity, price or duration violations explain the reason and retain the original draft without automatically repricing it or reducing its minimum purchase quantity. Each bulk confirmation rechecks current policy against the original request; policy changes do not silently rewrite previewed terms.

Check actual items, quantity, currency, payment, fees and net proceeds on confirmation. A large quantity may use a single display icon; the lore contains the authoritative quantity.

Final bundle confirmation identifies one whole bundle, its complete entry count, total item quantity, bundle price and fees. Open “View all bundle items” to inspect every item's real properties and quantity. Returning keeps the original quote; previewing does not remove items, reprice or submit again. Containers in the list retain read-only nested previews.

## Business identities and advanced procurement

Advanced conditions combine materials, readable text, enchantments, durability, provider source/business ID, CustomModelData, PDC tag names and administrator-exposed scalar fields.

- Business IDs come from enabled public APIs for real held items, not guesses from names, lore or NBT. Bridges cover ItemsAdder, Oraxen, Nexo and MMOItems; API availability is not certification of every live version.
- Up to 32 PDC key names may be required simultaneously. Tags are not arbitrary NBT paths or scripts.
- Editable scalar fields must appear in `items.exposed-fields`. String, number and boolean values support literal equality or contains matching, without regular expressions or scripts.
- OR alternatives come from declarative administrator configuration. The player editor does not offer free scripting.
- Every edit validates a detached candidate before replacing the draft. Rejected edits leave the original draft intact.

These rules never relax fidelity or opaque-data admission. When a verified business identity cannot safely scope unknown properties, use a complete EXACT sample.

## Fees and restrictions

Existing `market.tax-bps` and `market.taxes` remain valid; 100 basis points equals 1%. New fee rules select the first matching row by permission, currency, order type and optional declarative item condition:

```yaml
fees:
  enabled: true
  rules:
    - id: sale-coins
      type: SELL
      currency: coins
      listing-fixed: 100
      listing-bps: 0
      seller-fixed: 0
      seller-bps: 500
      buyer-fixed: 0
      buyer-bps: 200
```

Fixed amounts use currency minor units. With `coins.scale: 2`, this example charges 1.00 to list. For gross 800.00, the buyer pays 816.00 and the seller receives 760.00, excluding the separate listing fee. With no enabled matching fee rule, legacy tax behavior applies.

Listing, buyer and seller fees are distinct. Orders retain their fee snapshot when configuration later changes. Partial fills allocate fixed fees and rounding over cumulative order turnover; the final fill receives the remainder. Cancellation returns unfilled escrow or frozen funds, without treating an already charged listing fee as refundable funds.

New fee rules combine the cumulative fixed share and percentage charge before rounding down, then subtract fees already collected. Whole-order fees remain unchanged and seller fees cannot exceed an individual fill's gross, so low-priced final items can still settle.

`policy` restricts new trading by world, player, item or creative mode. The first matching `policy.limits` permission row controls order count, quantity, price range, duration, cooldown and allowed currencies. GUI, commands and developer requests use the same rules. Existing owned assets retain their permitted exit paths.

## Wallets, new currencies and automation

Existing Vault, PlayerPoints, CoinsEngine and ExcellentEconomy identities remain unchanged.

| Provider | Unit and requirements |
| --- | --- |
| `experience` | Vanilla experience points; `scale: 0` |
| `experience-level` | Vanilla levels; `scale: 0`, mutually exclusive with points in one network |
| `item` | Actual item currency; `scale: 0`, a saved real `item-sample` and positive integer `denomination` |

Experience points and levels are different measurements, not a linear exchange rate. An item currency compares the complete sample. Changing its sample or denomination changes currency identity; do not replace them while existing funds depend on the old identity. Gateways, real balance, player availability, inventory space and receive capacity still apply.

Shortfall top-up reads actual funds and the actual shortage. A successful deposit reloads the order and quote before another confirmation; it does not silently execute the earlier trade. Depositing and buying have separate results.

Future-income withdrawal, login withdrawal and automatic claiming are separate opt-in features and default off. Future income creates distinct withdrawal reservations. Disabling the feature does not automatically release existing reservations; review or explicitly release them in the reservation page.

Automation uses bounded batches and pauses for unavailable gateways, insufficient space, changed sessions or unresolved external outcomes. UNKNOWN is never treated as failure to justify another execution.

## Favorites, searches and notifications

Save up to 256 favorite orders and 20 searches. Searches preserve type, currency, material, readable text, source, category, price bounds, single/bundle kind, featured state and sorting. Price bounds are non-negative integers in minor units: 123 means 1.23 for scale 2.

Saved searches and subscriptions retain the main market's material-name matching. For example, “钻石” can still find diamond procurement orders without an exact sample. Editing the search text updates these material matches while retaining the other filters.

Name searches include both formatted names and readable text without color codes, so per-character gradients do not split keywords. When a modern item has no custom display name, its public API `item_name` is used; a player's custom display name takes priority. Names support presentation and discovery without replacing business IDs or full-property matching.

Subscribe to new matching orders. Personal notices include matching listings, finished favorites, purchases, sales and auction outbids. Same-type notices merge by minute, deduplicate replay and retain up to 100 entries. Personal notification preferences apply to future notices. Offline notices persist in the shared market.

Login reports actual unread entries. Online polling runs every 15 seconds and combines changes into one reminder. Delivery never marks entries read; opening a notice or explicitly marking all read updates the durable status.

Public broadcasts and Discord forwarding default off. Broadcasts use independent node cursors and 60-second grouping by currency/type. Discord retains the message identity for each actual order, updates remaining amounts/bids and deletes terminal orders. Network rate limits and daily quotas apply; mentions, player identities, raw item names/lore/NBT and executable trade buttons are excluded. An uncertain publication is retained as UNKNOWN and is not blindly reposted.

Set `notifications.discord.language` to `zh_CN`, `en_US` or the default `auto`. `auto` inherits the server's `language`; if that is also `auto`, Discord uses Chinese. Currency labels use that language's `display-name`, and amounts respect the configured currency precision. Unit prices, whole-bundle prices, starting lot prices and current lot bids have distinct labels. Buy orders without a sample show only public materials and the condition mode; inspect full conditions in-game. Bundles report their actual item count, and auctions report the complete lot quantity. Customize wording under `community.discord` in `lang/community_<language>.yml`. Discord configuration and its display snapshot are fixed at startup; restart normally after changing them instead of using `/km reload`.

## Seller statistics and reference prices

Seller profiles and rankings use observed committed trades, separately for each currency. Their 1/7/30-day windows use UTC calendar days, not exact rolling 24/168/720 hours. No observations display as absent; failed reads do not appear as zero.

Rankings can switch between net income, completed trade count and quantity sold. Open a seller's profile for its statistics and orders. Seller order pages also include completed orders; their states determine whether trading is still available, and historical quantities are not remaining stock.

Discovery and seller indexes each support up to 1,024 players. A full discovery index rejects a new favorite/subscription before saving its preferences; an unsubscribed manual saved search remains available. A full seller index preserves exact individual statistics and makes complete rankings explicitly unavailable, rather than presenting a partial network ranking.

Public price references group complete comparable items in one currency and offer 24-hour, 7-day and 30-day windows. Median uses trade unit prices, while mean is quantity-weighted. Different item properties, bundle compositions and currencies are not merged. A reference is not a guaranteed executable quote or exchange rate.

## Administration and risk review

Read-only audit uses `kitemarket.audit.all`; management writes use `kitemarket.manage`. Actions preview specific targets and actual assets, require a reason and confirmation. Administrator transfers, item grants and listings use existing administrator funds/assets, rather than inventing player balances. Batch cancellation reports individual successes, skips and pauses.

Trading bans prevent new listings, purchases, supplies and bids without clearing the player's wallet or items. Withdrawals, claims and cancellation of owned orders retain their normal main-license and session rules. Unbanning restores access to new trades.

Inspect unresolved operations and structured evidence before deciding their outcome. A current wallet or inventory screenshot alone cannot prove a past external effect. Bounded JSONL exports in the plugin's `exports/` directory report record count, truncation and digest. Retention only expires generated exports; it does not delete financial records, assets, orders or unresolved evidence.

Export retention defaults off; zero days keeps exports indefinitely. After an administrator sets a duration, a background hourly pass checks at most 500 exports for this network, verifying both the header creation time and file modification time. Invalid, foreign-network and incomplete exports remain.

Local risk analysis uses committed trades, excluding bids, holds and UNKNOWN outcomes. The Isolation Forest requires all three: 512 trades, 10 players and 24 hours of history. Rules can produce review signals while the model is learning. Training uses 30 days of history; the bounded relationship graph uses 7 days.

Repeated counterparties, concentrated turnover, short funding cycles, comparable-price outliers and model anomalies require manual interpretation. Friends, guilds, rare expensive items and sparse markets can be normal. A missing comparable baseline never makes absolute high price alone a price violation. Scores are not cheating probabilities. Cases retain watch/false-positive/normal/manually-confirmed status, notes and review history without automatic penalties.

The default case limit is 10,000. Only normal or false-positive cases with no outstanding cloud request may rotate out. Watch, confirmed and uncertain cloud evidence remain. If no case can rotate out, analysis pauses before advancing past the triggering trade and displays a capacity notice. Administrators can still review retained cases; ordinary trades continue.

## Scoreboards, NPCs and permission plugins

These optional integrations provide display values and entry points while retaining market permissions and confirmation. Install the corresponding plugin and restart normally. Missing or incompatible APIs make that integration unavailable while the base market remains usable. Consult verification records for specific supported builds.

Use PlaceholderAPI in scoreboards or other placeholder-aware displays:

| Placeholder | Meaning |
| --- | --- |
| `%kitemarket_state%` | Current market initialization state |
| `%kitemarket_network_id%` | Current market network UUID |
| `%kitemarket_wallet_coins_available%`, `%kitemarket_wallet_coins_frozen%` | Available and frozen `coins` amounts; replace `coins` with the configured currency ID |
| `%kitemarket_luckperms_primary_group%` | The already-loaded LuckPerms player's primary group |

Wallet values come from a short-lived cache without blocking the placeholder thread. Unready services, expired caches and failed queries return empty values rather than zero balances. Placeholders must not authorize payments or determine a trade's success.

Citizens opens the market only for explicitly configured NPC IDs:

```yaml
integrations:
  citizens:
    npc-ids: [12, 27]
```

Replace the sample IDs with actual NPC IDs and restart normally after changing them. Right-click opens the same `/km` interface and retains player permission checks. LuckPerms reads only an already-loaded primary group; trading policies use effective Bukkit permissions rather than granting access from a group name.

## Optional cloud review and privacy

Cloud review defaults off and requires explicit administrator confirmation for a specific case. The default network quota is 20 requests a day:

```yaml
risk:
  enabled: true
  cloud:
    enabled: false
    endpoint: 'https://your-provider.example/v1/chat/completions'
    api-key: ''
    model: ''
    daily-limit: 20
    maximum-request-bytes: 16384
    maximum-response-bytes: 32768
    timeout-millis: 15000
```

The selected HTTPS service must accept compatible chat-completions responses. The API key authenticates the configured endpoint and is not a model evidence field. Evidence contains purpose-separated network HMAC aliases, allowed signals and numeric measurements, excluding real player UUIDs/names/IPs, lore, NBT, administrator notes and raw events.

Requests and responses have size and time limits and never follow redirects. Responses must cite evidence from this case and use the defined advice fields. Unknown actions, tool calls and foreign references are rejected. Cloud advice cannot execute market operations, confirm external trades or punish players. Local analysis remains independent when cloud review is off.

The shared case request identity and daily quota commit together before sending. Other nodes reuse the in-progress status or stored advice. Timeout, request failure, rejected advice or interruption leaves an unconfirmed outcome and consumed quota, blocking another request for that case even after restart. Continue local review and check the selected provider.

## Common outcomes

| Outcome | Next step |
| --- | --- |
| Inventory or receive capacity is insufficient | Make space, reread and confirm; assets remain owned |
| Order or quote changed | Refresh and confirm the current quote |
| Session expired | Reenter the market; old screens cannot write |
| External transfer/delivery is UNKNOWN | Retain the original operation; audit and explicitly resolve it without replay |
| Learning or no comparable baseline | Accumulate genuine trades rather than inventing zero values |
| Risk evidence capacity reached | Review retained cases; analysis resumes when a resolved case can rotate out |
| Cloud outcome unconfirmed | Retain the original request and quota; continue local review without resending |
| Cloud disabled, quota used or response rejected | Continue local manual review |
