# KiteMarket v1.1 候选版本用户指南

本文对应 v1.1 候选实现，尚不代表正式发布或全部环境已完成实服验收。正式构件、实际验证范围与发行说明以最终发布记录为准。安装及既有数据处理见 [UPGRADING.md](https://www.kitemc.com/kitemarket/operations)；不承诺 v1.0.0 无缝升级。

常用候选入口为 `/km lots`（整包/批量）、`/km automation`（个人自动化）、`/km community`（收藏/通知）、`/km prices`（公开价格），管理员使用 `/km risk`（只读审计）和 `/km tools`（管理写入）。对应功能权限与确认仍生效。

## 安装、数据库与现有市场

v1.1 全新安装使用独立服务器／插件数据目录。默认持久 SQLite 文件适用于一个市场节点；多服务器共享市场使用独立、空的 MySQL/MariaDB 数据库，不让多个游戏节点共用同一个 SQLite 文件。每个节点使用唯一 `network.node-id`，同一市场保持相同网络、游戏版本、物品配置与币种身份。

已有 MySQL/MariaDB 配置不会被自动换成 SQLite。如需处理已有市场，先完整备份数据库、配置、原运行包、玩家及经济数据，并在独立副本检查迁移和恢复，再决定原环境的切换方案。保留原订单、钱包、冻结、领取和未决证据；不要删库、用新安装配置覆盖旧身份、手改金额、重复激活或混跑新旧协议。

基础插件提供完整原版 GUI。开发者可通过配置与公开 Java SDK 制作自己的 ItemsAdder 界面；真实物品、受保护动作、权限和交易确认仍由服务端提供。

服主可在配置文件中选择需要的交易模式，例如只开放竞拍：

```yaml
market:
  enabled-types: [AUCTION]
```

默认 `[BUY, SELL, AUCTION]` 分别开放收购、一口价和竞拍。至少保留一种模式；空列表、未知模式和非列表配置会被拒绝，重载失败保留上一有效配置。首页、新建向导、整包和管理员代上架只显示启用模式，命令与 SDK 同样不能绕过开关。仅剩收购模式时不会显示整包/批量发布入口。

共享市场的所有节点须使用相同值，并分别执行 `/km reload`；策略代次不一致的节点会拒绝新交易。关闭模式不会取消旧订单、改写期限或清退市场；旧单仍可查看，按原规则撤回、到期退回或完成已有竞拍结算，钱包与领取不受影响。

## 单品、整包、批量与容器

| 操作 | 数量与价格语义 |
| --- | --- |
| 一口价单品 | 单价 × 本次购买数量；允许部分购买 |
| 收购 | 单价 × 本次供货数量；实际交付物必须满足全部条件 |
| 竞拍 | 出价是整个拍卖标的的总价，不是每件单价 |
| 整包 | 多项真实资产组成一个不可拆分标的；价格是整包总价，成交一次交付整个组合 |
| 批量上架 | 多个独立订单；逐项预览实际物品、费用与结果，不把成功项当作整批都成功 |

出售的最低购买量可以在发布条款页设置。余量低于最低量时，只能买完全部余量；整包不使用拆件购买。相同材料但不同名称、耐久、附魔、业务 ID 或完整属性的物品不能因“看起来一样”而混成同一精确样品。

容器预览只展示真实保存内容，不允许从预览页取物。容器或嵌套内容无法完整往返保存、结构不受支持或超过限制时，发布会被拒绝；换一个展示图标不会改变准入结果。售出、撤回或到期后，物品按真实资产进入领取箱；背包空间不足时保留待领，不直接丢到地上。

已发布整包在订单详情打开内容页，逐项查看真实数量；已验证容器可继续只读查看内部内容。领取箱按来源分类并分页，勾选或全选当前页后查看明细、明确确认，单批最多36项。空间不足的项跳过保留；未确认结果、会话变化或离线会停止后续项，不重复已领取项，也不会自动续做其他页。

批量中的每份订单仍需人工确认。未发布选择和批量计划仅在当前会话保留，退出或重启后不自动续做；已经执行的单笔操作、资金和结果持久保存。

单品按完整所选数量、批量按每个独立组、整包按一个标的检查当前发布策略。数量、价格或期限超限时显示具体原因并保留原草稿，不自动调价或降低最低购买量。每份批量订单进入确认时重新检查当前策略和原请求，策略变化不会静默改写已经预览的条件。

发布前检查确认页的实际物品、数量、币种、支付、费用和净收入。不要用列表角标判断整包数量；数量较大时图标可能只显示一个，准确数量以说明为准。

整包最终确认以“1包”为标的，同时列出完整商品项数、包内总数量、整包总价与费用。点击“查看整包全部物品”逐项核对真实属性和数量；返回仍是原报价，未确认前不会扣物、重新计价或重复提交。清单内的容器可继续只读预览。

## 业务身份与高级收购

高级条件可同时限制材料、名称、Lore、附魔、耐久、物品来源/业务 ID、CustomModelData、PDC 标签和管理员开放的标量字段。

- 业务 ID 从手持实物及启用桥接的公共 API 读取；不会从名称、Lore 或猜测的 NBT 得出。当前桥接来源为 ItemsAdder、Oraxen、Nexo、MMOItems，是否可用看实际 API 状态，不能据此宣称所有版本都已认证。
- 标签是必须同时存在的 PDC 键名集合，最多32个；不是任意 NBT 路径或可执行脚本。
- 字段编辑只列出 `items.exposed-fields` 开放的字符串、数字或布尔标量。条件使用按原样的精确相等或包含，不运行正则或脚本。
- OR 规则只由声明式管理员配置读取。玩家 GUI 不提供自由脚本编辑。
- 每次更改先校验独立候选副本；范围无效、来源未确认或字段未开放时，原草稿保持。

这些条件不放宽物品保真或未知数据准入。未知属性无法用已确认业务身份安全限定时，仍须使用完整 EXACT 样品；EXACT 保存完整比较身份，不是把显示名称当作真实属性。

## 费用与限制

已有税率继续使用 `market.tax-bps` 或 `market.taxes`，`100` 基点为 `1%`。新 `fees.rules` 按配置顺序取第一条匹配规则，可按权限、币种、订单类型和声明式物品条件区分：

```yaml
fees:
  enabled: true
  rules:
    - id: sale-coins
      type: SELL
      currency: coins
      listing-fixed: 100
      listing-bps: 0
      seller-fixed: 0
      seller-bps: 500
      buyer-fixed: 0
      buyer-bps: 200
```

费用中的固定金额使用币种最小单位。上例在 `coins.scale: 2` 时：上架费1.00；成交金额800.00，买方支付816.00，卖方净收入760.00，上架费另计。没有启用且匹配的新费用规则时，沿用旧税率行为。

上架费、买方手续费、卖方手续费分别展示。发布时的费用规则保存到订单；后来重载费用不会改写旧订单。部分成交按整单累计金额分摊固定费用和舍入，最终一笔结清余数，拆分购买不会重新按每笔收取整单固定费用。撤回会返还未成交托管或冻结，不把已收上架费当作待退余额。

新费用规则将累计固定费用份额与比例费用合并后向下取整，再扣除已经收取的费用。整单总费用不变，单次卖方费用不会超过该次成交金额；金额很小的尾单也可正常结清。

`policy` 可按世界、玩家、物品和创造模式限制新交易；`policy.limits` 第一条匹配权限规则可设置挂单数、数量、价格范围、期限、冷却与允许币种。限制通过交易确认与数据库校验执行，GUI、命令和开发者请求使用同一规则；改显示位置不会放宽限制。被禁止新交易的玩家仍可按授权与会话条件退出已有资产。

## 钱包、新币种与自动化

旧 Vault、PlayerPoints、CoinsEngine、ExcellentEconomy 配置继续使用原币种 ID 与网关。新增：

| `provider` | 单位与要求 |
| --- | --- |
| `experience` | 原版经验点，`scale: 0` |
| `experience-level` | 原版等级，`scale: 0`；同一网络不得同时配置经验点模式 |
| `item` | 真实物品币，`scale: 0`；需要保存真实 `item-sample` 与正整数 `denomination` |

经验点和等级不是线性兑换的同一种计量，整个网络必须二选一。物品币按完整样品比较，材料相同不等于相同货币；样品或面额变化会改变币种身份，不能在存在原币种资金时直接换配置。充提仍受指定网关、玩家存活状态、真实余额、背包空间和接收容量限制。

缺口补款读取真实余额并显示缺口；充值成功后重新读取订单与报价，再由玩家确认，不依据旧报价静默成交。充值成功与购买成功是两条独立结果。

个人自动化包含“未来成交收益提现”“登录提现”“自动领取”，默认关闭，分别确认开启。未来收益会建立独立提现预约；关闭功能不会自动释放已建立的预约，需到预约页查看或明确释放。预约状态、冻结、未领取资产与普通可用余额分别显示。

自动化按有界批次执行。网关不可用、空间不足、会话变更或存在未确认外部结果时暂停；不会把 UNKNOWN 当成失败再执行一次。先核对原操作，再继续相关充提或领取。

## 收藏、保存搜索、订阅与通知

从订单页收藏，在个人社区页管理；每人最多256个收藏。保存搜索最多20个，记录类型、币种、材料、可读文字、来源、分类、价格区间、单品/整包、展示位及排序。价格区间输入为最小货币单位的非负整数，例如两位小数币种中 `123` 表示 `1.23`。

保存搜索和订阅保留主市场的材料名称匹配。例如“钻石”仍可找到没有精确样品的钻石收购单；更改搜索文字时会同步更新材料匹配，其他筛选条件保留。

名称搜索同时使用格式化名称与去除颜色码后的可读名称，逐字渐变不会把关键词拆开。现代物品没有自定义显示名时，读取公开 API 提供的 `item_name`；玩家自定义显示名优先。名称用于展示和搜索，不代替业务 ID 或完整属性比较。

搜索可选择订阅新匹配订单。个人通知包含匹配新单、收藏终态、购买/售出成交及拍卖被超价。同类型事件按一分钟合并，重放去重，保留最多100条；个人开关可以关闭后续通知。通知在网络中持久保存，离线不会因玩家没看到聊天而丢失。

登录时提示真实未读数量，在线检查每15秒最多合并一条聊天提醒。提醒不会自动标为已读；打开通知详情或明确“全部已读”才更新持久已读状态。聊天只给少量短订单引用，完整目标在详情中查看。

公开游戏广播和 Discord 转发默认关闭。广播按节点独立游标及60秒合并，按币种与类型分组。Discord 按真实订单保存消息身份，创建后更新余量/竞价，终态删除；同一网络限频与每日额度，关闭提及，不包含玩家身份、原物品名称/Lore/NBT或交易执行按钮。发送结果未知时保留 UNKNOWN 并停止盲目重复创建消息；这不会回滚已经完成的游戏交易。

`notifications.discord.language` 可设置 `zh_CN`、`en_US` 或默认的 `auto`。`auto` 沿用服务器 `language`，服务器同样为 `auto` 时使用中文。币种名称读取对应语言的 `display-name`，金额按实际币种精度显示；单价、整包总价、起拍总价和当前竞价总额分别标注。收购无样品时只展示公开材料和条件模式，具体条件仍在游戏内查看；整包展示实际物品总数，拍卖展示整件数量。文案可在 `lang/community_<语言>.yml` 的 `community.discord` 中配置。Discord 配置及展示快照在启动时固定，修改后正常重启，不使用 `/km reload` 更新。

## 卖家资料、价格参考与排行

卖家页与排行榜基于已观察的已提交成交，每个币种独立累计。卖家统计支持1、7、30个 UTC 日历日窗口；不是精确滚动24/168/720小时。没有观察数据时显示无数据，读取失败不冒充零。

排行榜可切换净收入、成交笔数和已售数量；点击卖家查看其成交统计与订单。卖家订单页包含其已完成订单，订单状态决定是否仍可交易，历史数量不表示仍有库存。

收藏/订阅发现索引和卖家索引各最多1024人。发现索引满时，新增收藏或订阅会明确拒绝，不留下半保存的偏好；未订阅的手动保存搜索仍可使用。卖家索引满后个人精确成交统计继续保存，完整排行榜明确显示不可用，不把部分卖家排行当成全网络排名。

公开价格参考以完整可比物品和同币种分组，提供24小时、7天、30天窗口。中位数是成交单位价中位数；均价按成交数量加权，并展示实际成交量。不同属性的稀有物品、整包组合或币种不能强行混成同一基线；参考价不是保证成交的报价或跨币种汇率。

## 管理、审计与风险复核

只读审计使用 `kitemarket.audit.all`，管理写入使用 `kitemarket.manage`。管理员操作先选择明确目标与实际资产，填写原因并确认；管理员钱包转账、真实资产发放和代上架消耗管理员已有资金/资产，不凭空修改玩家余额。批量撤单只处理预览的当前批次，逐项返回成功、跳过和暂停结果。

交易封禁阻止被封禁玩家新发布、购买、供货和竞拍，不清空其钱包或物品；按主授权和会话规则，提现、领取及本人撤单仍可使用。解除封禁后才恢复新交易入口。

操作结果不明确时先查看操作、收据和结构化证据，再作明确复核；当前余额或背包截图不能单独证明历史外部副作用成功。导出是有界 JSONL，保存在插件 `exports/`，包含条数、截断说明和摘要；保留策略只清理本网络生成的过期导出，不删除钱包、账本、资产、订单或未解决证据。

导出保留默认关闭，`0` 天表示一直保留。管理员设定天数后，后台每小时检查一次，每次最多检查500个本网络导出；同时核对文件头中的创建时间和文件修改时间。无效文件、其他网络文件和未完成导出保留。

风险分析只处理已提交成交，不把出价、冻结或 UNKNOWN 当成成交。真正 Isolation Forest 本地模型需要同时满足512笔成交、10名玩家、24小时跨度；不足时显示学习进度，规则线索仍可工作。模型按30天历史训练，关系图使用有界7天记录。异常分数不是作弊概率。

频繁固定对手、成交集中、短时资金闭环、同类高价和模型异常都是需要人工核对的线索。朋友、公会交易、稀有高价物品和低样本可能正常；没有同类基线时不会只因绝对价格高就认定异常。案件可标记待观察、误报、正常或人工确认可疑，并保留备注与复核历史；不会自动罚款、封禁或撤单。

案件默认最多10000条。容量满时只轮换已标记正常或误报、且没有未完成云端请求的案件；待观察、确认可疑或云端结果未确认的证据保留。无可轮换空间时分析游标停在触发成交之前，界面显示容量提示，管理员仍可打开案件复核；普通交易继续执行。

## 计分板、NPC 与权限插件

这些可选集成只提供显示与入口，不取代市场权限或交易确认。安装对应插件后正常重启；未安装或 API 不兼容时，其集成显示不可用，基础市场仍可独立使用。具体版本支持以对应构件验证记录为准。

PlaceholderAPI 可在计分板等支持占位符的位置读取：

| 占位符 | 含义 |
| --- | --- |
| `%kitemarket_state%` | 当前市场初始化状态 |
| `%kitemarket_network_id%` | 当前市场网络 UUID |
| `%kitemarket_wallet_coins_available%`、`%kitemarket_wallet_coins_frozen%` | `coins` 钱包的可用与冻结金额；将 `coins` 换为实际币种 ID |
| `%kitemarket_luckperms_primary_group%` | LuckPerms 已加载玩家的主组 |

钱包数值使用短时缓存，不阻塞占位符线程。未就绪、缓存过期或查询失败时返回空值，不能据此当作零余额；占位符不用于扣款或判断一笔交易是否成功。

Citizens 只为明确登记的 NPC 开放右键市场入口：

```yaml
integrations:
  citizens:
    npc-ids: [12, 27]
```

将示例 ID 替换为自己服务器的真实 NPC ID，修改后正常重启。点击打开同一个 `/km` 界面，仍检查玩家权限。LuckPerms 集成只读取已经加载的主组；实际权限规则使用玩家有效的 Bukkit 权限，不凭组名授予交易权限。

## 自配云端复核与隐私

云端默认关闭，只在管理员确认具体案件后发送，默认网络每日20次：

```yaml
risk:
  enabled: true
  cloud:
    enabled: false
    endpoint: 'https://your-provider.example/v1/chat/completions'
    api-key: ''
    model: ''
    daily-limit: 20
    maximum-request-bytes: 16384
    maximum-response-bytes: 32768
    timeout-millis: 15000
```

服务需兼容 chat-completions 响应，并使用 HTTPS。API key 用于你配置端点的 HTTPS 鉴权，不作为模型证据字段。向模型发送的证据只有按网络 HMAC 分离的假名、受控信号及数值；不发送真实玩家 UUID、姓名、IP、Lore、NBT、管理员备注或原始事件。

请求和响应都有大小与超时上限，不跟随重定向。返回结果必须引用本案证据，只接受规定的建议字段；未知动作、工具调用或其他案件引用会被拒绝。云端建议不能执行市场操作，也不会替管理员做处罚或确认交易。费用和隐私条款由管理员选用的服务决定，关闭云端后本地分析仍可独立工作。

同案请求身份和当日额度先在共享存储一起提交，其他节点只读取正在进行的状态或已保存建议。超时、请求失败、响应被拒绝或发送节点中断后结果不明确时，保留“结果未确认”记录与已占额度，禁止此案重复发送，重启也不会重发；继续本地复核并向所选服务核对。

## 常见结果与下一步

| 结果 | 处理方式 |
| --- | --- |
| 背包或接收容量不足 | 腾出空间后重新查看和确认，资产保留 |
| 订单、报价或条件已变化 | 刷新，再按新的实际报价确认 |
| 会话过期 | 重新进入市场，旧页面不得继续写入 |
| 外部充提/交付 UNKNOWN | 保留原操作与资产；管理员核对后明确解决，勿重放 |
| 风险学习中、价格无基线 | 等待真实成交积累，不用合成零或绝对高价代替数据 |
| 风险证据容量已满 | 继续打开原案件复核；有可轮换已解决案件后恢复游标 |
| 云端结果未确认 | 保留原请求及额度，不重发，继续本地复核 |
| 云端关闭、额度不足或结果被拒绝 | 继续本地人工复核，不影响普通交易 |

GUI 外观与真实原始槽位见 [GUI-CONFIGURATION.md](GUI-CONFIGURATION.md)。开发者 API、导入和升级分别使用对应专题文档，不通过 GUI 文本或脚本绕过核心约束。
